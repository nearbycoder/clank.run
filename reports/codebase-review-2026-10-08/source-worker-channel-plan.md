## Established native feasibility

The private socket prototype completed on genuine immutable Docker images for Node22.16.0 and Node26.10.0, paired with the same exact native host runtime versions. The application kept the Docker default seccomp/AppArmor policy, zero effective capabilities, no-new-privileges, non-root1000:1000, read-only root, production memory/CPU/PID/tmpfs/log settings, app/data mounts and bridge network. Its extra channel mount was read-only and contained only its diagnostic socket.

Unmodified framework SQLite workers ran on the host through the existing default Linux namespace implementation. Fixed backup, inspection and integrity verification succeeded; independent native SQLite reads confirmed the two exact snapshot records and unchanged source bytes. Both clients refused altered authentication, binding, operation, sequence, unexpected fields and an exact replay. Each owned container was removed only after exact identity validation and a natural successful exit; each host server closed naturally. No worker namespace identity was independently sampled, and no complete host certificate is claimed.

The first attempt exited before container creation; its original host stderr was not captured. Direct native UID1000 directory opens reproduced errno13 on both root-owned traversal-only diagnostic parents. Making the new fixture parents readable resolved host readiness; this is a reproduced setup deficiency, not a recovered original stderr claim. The second attempt stopped before container start because the fixture asserted an AppArmor runtime profile in pre-start metadata. The corrected fixture reads actual process AppArmor enforcement, effective capabilities, no-new-privileges and seccomp. Both failures are retained; neither is reported as a passing test. No Docker security policy was relaxed.

See `source-worker-channel-feasibility.json` for exact image IDs, native process security observations, results, cleanup, hashes and evidence limitations. The owned VM root was additively expanded from12 to13GiB after exact PID/birth, disk inode, QMP mapping, filesystem UUID and GPT checks. Its boot/EFI partitions and source data were preserved. ## Production integration boundaries

The first code change narrows the existing constructor-minted source token to the three initialization operations below. It validates exact backup names, temporary UUIDs and four genuine retained directory capabilities, then preserves immutable own-data arguments and capabilities across admission waits. Its internal transport projection contains only an opcode and generated identifiers. This implements the source-side projection prerequisite; provider capability reconstruction, authenticated transport and coupled launch remain pending.

Native review reproduced successful inspection and backup of an unapproved sibling SQLite database on the original main. A second review of the unpublished candidate reproduced argument replacement during scheduler admission; an immutable copy now keeps the worker on its approved snapshot. Fourteen new scope cases and the complete 103-case source-runtime selection pass on Node22, Node24 and Node26. The copied-runtime selection uses genuine source tokens and default Linux workers, with explicitly scripted Docker-domain/catalog setup. Final adoption, release checks and protected delivery are recorded separately in the source-task review.

The diagnostic HMAC, fixed paths and fixture counters are a feasibility prototype. They must not be promoted directly into provider authority or used as proof that a source grant is ready. Production work needs the following complete path.

1. **Coupled launcher ownership.** Mint the worker channel only from a genuine owner-bound provider bridge and the exact retained source grant. Verify the current daemon and immutable container identity, actual image, all labels, UID/GID, app/data/catalog/socket mount sources and inode identities, default security, resource settings and topology. Existing created/started acknowledgments remain historical observations. An unknown or changed mount/daemon/container refuses admission. Do not adopt a stale socket or a replacement source directory after restart.
2. **Provider worker capability.** Bind a private WeakMap capability to the native grant/catalog, provider-owned data-directory pins and exact source database basename. No caller-supplied callback or serialized object may mint this capability. Guard the retained owner, domain, index, catalog mirror/version, binding, incarnation and revocation before queueing and after every await, immediately before spawn/stdin, after actual child close and before returning a result. Host workers must always use namespaces and existing resource bounds, including when the surrounding hosting scope selects trusted-process mode.
3. **Narrow task projection.** Support only the three initialization operations used by `openBackupManager[SQLITE_INTERNAL].source`: stageSQLiteBackup, inspectSQLite and verifySQLite. Requests cannot select SQL, modules, arbitrary operations, host paths, source files or worker arguments. The source database comes from the coupled mount capability. Other files must be exact generated snapshot/verification names inside the source incarnation's pinned private base directory. Retain directory descriptors on both sides; reconstruct host capabilities instead of interpreting client descriptor numbers as host descriptors. Reject traversal, symlinks, replacements, system directories and sibling projects.
4. **Authenticated bounded transport.** Derive a channel-specific key from the retained control secret with domain separation. Authenticate the complete protocol version, binding digest, exact container/incarnation, monotonic sequence, fresh nonce, opcode and canonical body/result. Enforce strict field sets, canonical JSON/UTF-8, small path-only request bounds, bounded fixed result shapes, socket limits, admission limits and deadlines before allocation or SQLite execution. Never place secrets in argv, Docker configuration, logs or ambient worker environments. Lost responses and uncertain operations fail initialization and preserve uncertain output rather than silently resubmitting or adopting it.
5. **Bootstrap integration.** Introduce an explicit opt-in bootstrap protocol that carries the fixed channel endpoint and attested mount/path projection. Keep the existing protocol and default helper path intact. Open the channel through the genuine source reader, retain it in the constructor-minted source context, and route only authenticated source-token operations. Preserve the original captured backend connection, reservation/write guards, key ownership, native completion readback and exact result. A channel response does not grant ordinary writes or establish a ready source.
6. **Close and revocation.** Closing either side stops new admission, cancels queued work, terminates only exact owned active workers and awaits their actual close before releasing pins or claiming a settled operation. Bound the full close deadline including scheduler wait. Catalog revocation or directory replacement during any queue/import/pin/spawn/worker/publication boundary prevents acknowledgment. Preserve uncertain staged files and unknown ownership. A closed socket, source epoch, process heartbeat or container exit alone is not a provider-wide stop receipt.
